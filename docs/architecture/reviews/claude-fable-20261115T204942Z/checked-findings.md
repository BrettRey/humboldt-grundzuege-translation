## Overall assessment

Fable recommends retaining the core architecture: hashed durable records and an append-only journal as authority, a rebuildable SQLite projection, and a read-only reader. Its central criticism is that storage protections are more complete than the correction workflow. The previously passing 103 tests establish their reported properties but missed the reproduced cases below. No implementation changes were made during this review.

## Disposition of the eight findings

1. **Limited edit coverage and absent Git baseline — confirmed, with a qualification.** The journal supports five fields: text body, three terminology fields and decision resolution. It does not support editing renderings, alignment members, evidence status or lexeme forms. The actual repository still has no commit. However, the original local release and historical snapshots preserve the initial baseline; the review’s suggestion that the earlier reading is simply gone overstates the current situation. Incremental unsupported edits need a safe history and authoring route. A local baseline commit requires separate authorization; none was made.

2. **Whole-row preconditions can block replay after unrelated base edits — reproduced.** A rejected terminology-rule proposal was recorded in a temporary fixture. Changing its base sense label, with the dataset fingerprint properly updated, made validation fail with `RevisionConflict: target no longer matches the proposal's original precondition`. The error omits the event ID. This is a compatibility constraint of immutable base rows and whole-row fingerprints. Fable’s proposed field-only check is a design option, not an automatically safe fix: a definition or context change can legitimately invalidate an interpretation even if its rule text is unchanged. An explicit metadata-revision/rebase policy is needed.

3. **Corrected-text apparatus and section discovery — reproduced; material workflow gap.** An accepted fixture text correction creates document, paragraph and word units. The new version remains retrievable by ID but disappears from the fixture’s declared §999 because its inherited title contains no section number. Importing a layout for that version fails with `layout text version missing`, since dataset expansion precedes journal projection. Titles currently keep real §1/§2/§147 corrections discoverable, but the apparatus-import limitation remains. Full version metadata, section membership and a supported route for reviewed segmentation/alignment must accompany text correction. Preserving the old links is appropriate; blocking new apparatus is a separate issue.

4. **CRLF form handling — reproduced at the HTTP boundary.** A submitted `\r\n` value survives draft download and acceptance. A rule differing only in line endings is accepted as a change. The paragraph splitter produces two paragraphs for LF and one for equivalent CRLF input. These checks exercised the real local HTTP endpoint with an encoded form; native-browser textarea serialization was not independently tested. Two current text versions contain line breaks. Consistent text normalization at the authoring boundary needs a regression check.

5. **Independent journal branches cannot be merged — reproduced.** Two fresh fixture copies each write sequence 1. Combining their otherwise valid, differently named event files makes load fail with `journal sequence is duplicated or incomplete`. The current protocol requires one authoritative journal writer; contributors can exchange fingerprinted drafts. There are zero real journal events currently, so no existing branch conflict needs recovery.

6. **Evidence and source-attachment UI — partly confirmed; one overstatement disproved.** The form says evidence identifiers “or objects”, while import accepts existing IDs only. Fourteen declared translation attachments exist locally but are rejected by the reader’s `sources/` confinement. Both are interface inconsistencies. However, an evidence-only dataset imported successfully, and its new evidence ID could immediately support a proposal. Thus there is a supported route for new evidence outside the form. Retain provenance entries when deciding how the reader should expose supporting translation artifacts.

7. **Storage complexity — design preference.** Sealing makes the public migration command unnecessary for ordinary builds; the JSON schemas and SQL catalogue also overlap. These observations do not demonstrate corruption or failed reproduction. Keep the working protections unless a concrete maintenance problem justifies simplifying them; schema generation must preserve the validation constraints it replaces.

8. **Real-data regression and operational limits — valid concerns, with qualifications.** The default suite uses synthetic fixtures. The full-data digest and table hashes already exist in `docs/architecture/verification.json` and migration provenance, although no routine command enforces that baseline. Comparing every future `validate` run to one fixed digest would also reject legitimate accepted edits; a version-aware regression/release comparison is preferable. Stale-lock recovery guidance and hard-link filesystem requirements should be clearer. No exFAT/FAT test or Python/SQLite compatibility matrix was run in this review.

## Recommended order

First complete the text-correction lifecycle, decide how contextual/metadata changes interact with journal preconditions, and normalize form line endings. Then clarify the current single-writer protocol, supported edit/evidence routes, attachment presentation and operational recovery. Establish a local Git baseline once authorized. Storage redesign is lower priority than these concrete gaps.
